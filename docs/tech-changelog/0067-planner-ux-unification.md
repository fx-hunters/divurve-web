## 변경 사유 (Why)

기존 Planner는 API와 데모가 서로 다른 화면 흐름을 사용했고 목표·현재 상태·Curve·
다음 행동을 별도 장면에 반복해서 보여주었다. Curve 좌표도 회차 순서에 맞춘 시각적
배치였기 때문에 사용자가 날짜와 누적 확보액의 관계를 읽기 어려웠다. 상황 비교와
적용 확인, 전체 계획 상세도 좁은 화면 안에 겹쳐 정보 밀도와 이동 경로가 불명확했다.

데이터 공급처와 저장 책임은 계속 분리하면서 같은 ViewModel과 표현 트리를 사용하고,
서버 또는 명시적인 데모 fixture가 준 날짜·금액만으로 계획 경로를 보여줄 필요가 있었다.

## 변경 내용 (What)

- API·데모 모두 `PlannerJourneyScreen`을 사용하고 adapter와 action 구현만 분리했다.
- 목표가 없을 때 회원은 서버 계약이 지원하는 마감형 목표를 생성할 수 있고, 데모는
  동일한 입력 UI로 세션 내 목표를 만들 수 있다. 회원 화면의 데모 둘러보기와 복귀도
  실제 계정 데이터를 변경하지 않는다.
- 목표 선택 뒤 현재 요약, 계획 Curve, 선택 지점과 다음 행동을 데스크톱 2열 또는
  모바일 1열의 한 장면으로 연결했다.
- Curve의 X축은 회차·실행·목표 날짜, Y축은 목표 배정 외화에서 회차 금액을 누적한
  값이다. 완료 회차는 실행 금액, 예정 회차는 서버 계획 금액, 건너뜀은 0을 사용한다.
  직선 경로로 표시하며 목표에 맞추기 위한 회차나 금액을 만들지 않는다.
- 목표별 활성 Plan이 없을 때에는 같은 통화의 전체 보유액을 목표 배정액으로 단정하지
  않고, Plan preview와 사용자 확인 뒤 create를 분리했다.
- 상황 비교는 기존 Curve와 변경 Curve를 같은 축으로 보여주는 단일 모달로 옮겼다.
  scenario preview만으로 저장하지 않으며 draft 식별자가 확인된 뒤 사용자가 적용을
  선택한 경우에만 apply한다.
- 회차 목록, 누적 금액, 계산 기준, 경고와 Plan 버전 이력을 공통 전용 상세 화면으로
  분리하고 URL 직접 진입·새로고침·브라우저 뒤로 가기를 앱 라우팅에 연결했다.
- `DIVISA + CURVE` 사용자 문구를 `DIVURVE`로 통일하고 SVG 기본 `<title>` 툴팁 대신
  접근 가능한 설명과 화면 안 지점 상세를 제공했다.
- 최신 develop의 공용 Spinner, AI 설명, Sidebar·Header, X-Ray·Home·Forecast 변경과
  Plan 버전 이력을 유지했다. Planner AI는 계획 이력에 이미 연결된 범위만 보존했다.

## 데이터·계산 경계

| 구분 | 처리 |
| --- | --- |
| API 목표·Plan·회차·scenario | 서버 응답만 사용하며 실패 시 demo fixture로 전환하지 않음 |
| 데모 목표·Plan·scenario | frontend fixture 또는 세션 내 로컬 입력만 사용하며 서버 쓰기 호출 없음 |
| 진행률 | 표시용으로 현재 확보액 ÷ 목표액을 0~100% 범위에 한정 |
| Curve X축 | 응답의 날짜 간격을 UTC 날짜 기준으로 좌표화 |
| Curve Y축 | 목표 배정액과 회차의 실행/계획 금액을 계약 의미에 따라 누적 |
| 누락·잘못된 값 | 임의 보정하지 않고 해당 지점 또는 기준선을 생략하고 안내 문구 표시 |

환율 전망, 미래 환율, 달성 확률, 추천 시점, 안전 비율, 임의 회차와 임의 금액은
프론트에서 생성하지 않는다.

## 영향 / 리스크

- 회원 목표 생성은 현재 계약상 마감형 목표만 제공한다. 반복형 입력은 데모에서만
  체험할 수 있으며 서버가 지원하는 것처럼 표시하지 않는다.
- 활성 Plan이 없을 때 Goal의 `heldAmount`는 같은 통화의 전체 보유액일 수 있으므로
  목표별 확보액으로 단정하지 않고 배정 후 확인이 필요하다고 안내한다.
- API preview/create/scenario/apply의 실제 서버 쓰기 동작은 운영·공유 서버에 검수용
  데이터를 만들지 않기 위해 mock 테스트로 검증했다.
- 화면 viewport별 실제 브라우저 육안 검수는 사용자가 최종 확인해야 한다.
- 기존 Fast Refresh, React `act(...)`, Vite chunk 크기 경고는 별도 후속 정리 대상이다.
