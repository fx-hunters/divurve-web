## 변경 사유 (Why)

공통 요구사항 1번("백엔드 API 호출 확인하기")에 따라, 프론트가 호출하는 모든 엔드포인트가
실제 백엔드 계약과 일치하는지 확인해야 했다. 이슈 #47 은 "다른 모든 이슈가 머지된 뒤 마지막에"
수행하도록 못 박혀 있었고, 지금이 그 시점이다.

점검이 필요했던 실질적 이유는 **틀려도 아무 신호가 없는 구조** 때문이다. 과거 두 건이 그랬다.

- `PairCode.parse()` 가 `_`·`/` 를 제거하고 6자리면 통과시켜, 명세에 없는 `JPY_KRW`·`EUR_KRW`
  요청이 400 없이 오래 살아 있었다.
- 프론트가 존재하지 않는 regime 값(`high`/`extreme`)과 비교해, 변동성 경고가 영구히 꺼져 있었다.

둘 다 컴파일도 테스트도 통과한 채 숨어 있었다. 같은 유형이 다른 곳에도 있는지 찾는 것이
이번 점검의 핵심 목적이었고, 실제로 **여섯 건 더** 나왔다.

## 변경 내용 (What)

- `docs/api-audit-2026-09.md` 신규 — 엔드포인트 **36개** 전수 표(프론트 호출 ↔ 백엔드 컨트롤러 ↔
  일치 여부), 불일치 목록(High 7 · Medium 6 · Low 8, 각 항목에 `수정함` / `후속 이슈 필요` /
  `BE 사안` 표기), "관대해서 조용히 어긋나는" 지점 정리, 확인 완료 항목, 미사용 백엔드
  엔드포인트 목록, 이슈 초안 10건(A~J).
- 이 변경 로그 파일.

**기능 코드는 한 줄도 고치지 않았다.** 이슈 #47 은 조사·문서화 작업이며, 발견한 불일치는
전부 이슈 초안으로만 남겼다.

## 영향 / 리스크

- 이번 변경 자체는 문서 추가뿐이라 런타임 동작·수치 변화가 **없다**.
- 다만 리포트가 기록한 계약 불일치는 실제 사용자 화면에 영향이 있다. 특히 H2·H3·H4 는
  **커버리지 100% 상태에서 살아남았다** — `src/test/api-fixtures.ts` 가 프론트 타입 기준으로
  작성돼 있어 백엔드가 계약을 바꿔도 테스트가 초록이기 때문이다. 이 구조적 문제는 초안 J로 남겼다.
- 근본 원인은 두 가지로 좁혀진다.
  1. `client.ts` 의 `toCamelCase(...) as T` — 응답 런타임 검증이 없어 필드가 통째로 없어도 `undefined` 로 조용히 렌더된다 (H2·H3·H4·M6).
  2. 라벨 조회 테이블의 `?? fallback` 관용구 — 모르는 서버 코드가 와도 예외 없이 흘러나가 경고가 영구히 꺼진다 (H5·H6·M3·M4). 과거 regime 버그와 같은 형태다.
- 리포트는 백엔드 `develop` `9d65c5c`(2026-09-08) 시점 스냅샷이다. 백엔드가 움직이면 낡는다.
  초안 A~D 착수 시 Swagger 로 재확인할 것.
