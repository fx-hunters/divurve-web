## 변경 사유 (Why)

전망 기간이 30일·90일 둘뿐이라 "너무 성기다"는 요구가 있었다. #45 당시에는 백엔드
`ForecastService.ALLOWED_HORIZON_DAYS` 가 `List.of(30, 90)` 이라 그 밖의 값이 400 이어서
**라벨 명확화까지만** 하고 선택지 확장을 후속으로 미뤄뒀다(변경 로그 0043).

그 선행 조건이 divurve-api#121(PR #131)로 해소됐다. 백엔드는 이제
`List.of(7, 14, 30, 60, 90, 180)` 을 받는다. #45에서 선택지 목록을 `as const` 배열 하나로
모아 뒀으므로, 이번 변경의 본체는 **배열 한 줄**이다. 나머지는 그 결과로 생긴 두 가지 문제를
처리한 것이다.

1. **선택지가 2개에서 6개로 늘면 컨트롤이 좁은 폭에서 넘친다.** 기존 토글은 한 줄 고정
   배치라 375px 에서 가로로 삐져나간다.
2. **긴 지평에서는 모델 성적표가 없을 수 있다.** 성적표는 지평 길이만큼의 과거 구간을 잘라
   검증한 결과라, 지평이 길수록 검증에 쓸 관측이 모자라진다. 그때 서버가 성적표만 거절하면
   기존 코드는 `Promise.all` 이 통째로 실패해 **팬 차트까지 사라진다.**

## 변경 내용 (What)

- **선택지 확장** — `types/forecast.ts` 의 `FORECAST_HORIZON_DAYS` 를 `[7, 14, 30, 60, 90, 180]`
  로 넓혔다. 타입(`ForecastPeriod`)·화면 칩 목록·요청 `horizon_days` 가 이 배열 하나에서 따라온다.
  기본값은 목록의 첫 값(7일)이 아니라 **30일로 고정**했다 — 가장 짧은 구간을 첫 화면에 두면
  팬 차트의 폭이 거의 보이지 않는다. 라벨은 기존 규칙 그대로 "향후 N일" 이다.
- **기간 컨트롤을 줄바꿈 칩 목록으로** — 그룹 라벨("전망 기간")과 `aria-describedby` 보조 설명은
  그대로 두고, 라벨을 칩 위 줄로 올린 뒤 칩 줄에 `flex-wrap: wrap` 을 줬다. 칩 하나는
  `white-space: nowrap`·`flex: 0 0 auto` 라 글자가 잘리지 않고, 줄이 모자라면 다음 줄로 넘어간다.
  칩 좌우 여백은 `1rem` → `0.75rem`, 글자는 `0.875rem` → `0.8125rem` 으로 줄이고 선택 여부를
  테두리(`--border` / `--border-subtle`)로도 구분한다. 색은 모두 토큰이다.
- **성적표 실패를 카드 하나에 가둔다** — `api/forecast.ts` 에서 `/forecast/model-performance`
  요청만 `ApiError` 를 삼켜 `performance: null` 로 돌려준다(그 밖의 오류는 그대로 던진다).
  묶음 타입은 이 한 필드만 다르므로 생성 타입을 건드리지 않고 `ForecastBundleView`
  (`Omit<ForecastBundle, "performance">` + nullable)로 감쌌다. 화면은 성적표 카드에만 안내
  문구를 넣고 팬 차트·요약·동인·일정은 그대로 그린다.
- **성적표 행 분리·팬 차트 데이터 조립 정리** — 성적표 행 묶음을 표현 전용 `ModelScoreRows`
  로 뽑았다(§7.2). `toFanChartData` 는 계열마다 `find` 로 훑던 것을 날짜 색인(`Map`)으로 바꿨다 —
  180일 지평이면 행이 수백 개라 기존 방식은 계열 수 × 행² 만큼 비교했다.

## 영향 / 리스크

- **요청 파라미터의 값 범위가 넓어진다.** 화면에서 고른 값이 그대로 `horizon_days` 로 나간다.

  | 항목 | 변경 전 | 변경 후 |
  |---|---|---|
  | 선택지 | `30` · `90` | `7` · `14` · `30` · `60` · `90` · `180` |
  | 기본값 | `30` | `30` (그대로) |
  | 그 밖의 값 | 400 | 400 (백엔드 목록 밖은 여전히 400) |

- **실제 응답 확인(2026-09-08, `USDKRW` · demo 토큰).** 여섯 지평 모두 두 엔드포인트가 200 이다.

  | horizon_days | `/forecast` | `/forecast/model-performance` |
  |---|---|---|
  | 7 | 200 | 200 |
  | 14 | 200 | 200 |
  | 30 | 200 | 200 |
  | 60 | 200 | 200 |
  | 90 | 200 | 200 |
  | 180 | 200 | 200 |

  `USDJPY` · `EURUSD` 의 7·180일도 200 이었다. 즉 **이슈가 우려한 400 은 현재 나지 않는다** —
  백엔드가 180일에서도 `folds: 24` 로 검증 결과를 돌려준다. 그래도 성적표 격리는 넣어 뒀다.
  검증 구간은 과거 데이터 적재량에 따라 달라지고, 성적표 하나 때문에 팬 차트가 사라지는 것은
  어느 지평에서든 옳지 않기 때문이다. 목록 밖 값(`45`)은 예상대로
  `VALIDATION_FAILED` 400 이다.

- **성적표 카드의 표시가 갈린다.**

  | 성적표 응답 | 변경 전 | 변경 후 |
  |---|---|---|
  | 200 | 수치 4종 표시 | 수치 4종 표시 (그대로) |
  | 4xx/5xx | **화면 전체가 에러 상태** | 성적표 카드만 안내 문구, 나머지는 정상 |
  | 네트워크·파싱 오류 | 화면 전체 에러 | 화면 전체 에러 (그대로) |

- **모바일 폭.** 375px 기준 카드 안쪽 가용 폭은 대략 310px 인데 칩 여섯은 한 줄에 440px 가량
  필요하다. 그래서 가로 스크롤 대신 줄바꿈을 택했다 — 스크롤 칩은 뒤쪽 선택지(180일, 이번
  확장의 핵심)가 화면 밖에 숨고 스크롤 가능하다는 표시가 없다. 줄바꿈은 두 줄이 되는 대신
  여섯이 모두 보이며, 폭이 얼마든 넘치지 않는다.
- `components/**` · `app/app.tsx` · `vite.config.ts` · 다른 화면은 손대지 않았다. 생성 타입
  (`api/generated/divurve-api.ts`)도 그대로 뒀다.
