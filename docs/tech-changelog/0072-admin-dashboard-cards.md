## 변경 사유 (Why)

대시보드를 실제로 띄워 보니 카드 셋으로는 운영 상태를 읽기 어려웠다. 넷을 더한다.
**모두 기존 API 로 끝나 백엔드 신규 작업이 없다.**

### 가입자 총계는 기다릴 필요가 없었다

#94(가입자 지표)가 백엔드 `#171` 을 기다리고 있었는데, `fetchAdminUsers` 가 이미
`totalElements` 를 주고 `isDemo` 필터도 있다. **백엔드가 진짜 필요한 것은 일자별 추이 버킷뿐**이다.
총계를 #99 로 떼어내 먼저 낸다.

### 첫 차트

대시보드에 차트가 하나도 없어 "늘고 있나 줄고 있나"가 보이지 않았다. `usage-summary` 가 이미
일자별 버킷을 주고 `recharts` 도 의존성에 있다. 토큰은 곧 비용이라 추이가 가장 값어치 있다.

## 변경 내용 (What)

### 먼저 카드를 파일로 갈랐다

카드를 넷 더 붙이면 화면 파일이 500줄을 넘어 AGENTS.md 7.2 의 God Component 기준에 걸린다.
카드마다 `dashboard/cards/` 로 옮기고 화면은 **배치만** 한다. 공통 상태 헬퍼는 `card-state.ts` 로 모았다.
동작은 바뀌지 않았고 기존 테스트가 그대로 통과했다.

### 새 카드 넷

| 카드 | 이슈 | 출처 |
|---|---|---|
| 가입자 (총계·실계정·데모) | #99 | `fetchAdminUsers` ×3 |
| AI 토큰 추이 차트 | #100 | `fetchAdminAiUsageSummary` |
| AI 결과 분해 5종 | #101 | `fetchAdminAiCalls` ×6 |
| 통화 마스터 상태 | #102 | `fetchAdminCurrencies` |

## 영향 / 리스크

**요청 수가 늘었다.** 카드마다 따로 부르는 설계라 대시보드 진입 시 요청이 여러 개 나간다.
집계용은 전부 `size=1` 이라 응답이 작고, 하나가 실패해도 나머지 카드는 그대로 선다.
결과 분해가 6개(총계 + 5종)로 가장 많다 — 부담이 되면 백엔드에 결과별 집계 엔드포인트를
요청하는 편이 낫다(이슈 #101 에 적어 두었다).

**프론트가 세지 않는다.** 가입자·결과 건수는 서버가 센 `totalElements` 를 읽는다. 목록을 받아
프론트에서 세면 페이지 상한에 걸려 부분 집계가 되고 그 숫자가 사실과 달라진다.
토큰 차트만 같은 날 버킷을 접는데, 이는 표시용 파생이고 각 버킷 값을 그대로 더한다(AGENTS.md 7.6).

**`fallback` 을 실패로 칠하지 않는다.** `admin-ai-call-vocabulary.ts` 가 이미 정해 둔 판단을 따랐다.
`quota_blocked` 는 실패도 성공도 아니지만 사용자에게는 서비스가 막힌 것이라 따로 세운다.
토큰 차트도 `model === null` 인 날은 LLM 을 부르지 않은 것으로 구분해, 토큰 0을 장애로 오해하지 않게 한다.

계산에 영향 없음.
