## 변경 사유 (Why)

기존 현재 확보액 중복 합산 수정과 데모 기록 복원을 인수했다. 단위 테스트만으로
완료 처리하지 않고 호출별 backend 계약, 격리 브라우저, 실제 배포본을 분리해 확인했다.
그 결과 다음 회차 기록 차단, 적용한 데모 계획이 다음 비교의 기준이 되지 않는 문제,
만료 세션이 refresh보다 데모 발급으로 먼저 넘어가는 경로가 추가로 확인됐다.

전체 UI 재설계, 데모 계획 생성기, 서버 저장 정책 확대는 이번 수정에 포함하지 않는다.

## 변경 내용 (What)

- 만료된 저장 세션은 bootstrap과 401 복구가 같은 단일 갱신 요청을 공유한다.
  갱신 실패 시 만료 세션을 보존하여 재시도하며, 회원을 조용히 데모로 바꾸지 않는다.
  명시적 로그아웃의 기존 세션 제거는 유지한다.
- 출처 확인용 X-Ray의 비인증 오류는 Planner 목표·계획 조회와 분리한다.
  Goal의 명시적 출처 meta를 우선한다. 401/403은 계속 오류로 전파한다.
  fixture로 대체하지 않고 출처 재확인 안내를 표시한다.
- 저장 Plan의 확보액은 그대로 사용한다. 결측·음수 입력을 0으로 위장하지 않는다.
  과거 완료 구간을 복원할 수 없는 모순 응답은 그 구간을 숨기고 이유를 표시한다.
  관찰 날짜는 확인된 계산 날짜와 완료 날짜 중 가장 늦은 날짜를 사용한다.
- 데모 1회차 뒤 2회차 기록을 허용하되 같은 진행 중 실행의 중복 요청은 차단한다.
  현재 적용한 시나리오를 다음 비교의 기준으로 사용한다. 기록 당시의 시나리오 ID를
  기존 sessionStorage 데모 UI 상태에 보관해, 이후 시나리오 변경이 과거 기록 금액을
  바꾸지 않게 한다. 금액·인증정보·회원 자산을 복제 저장하지 않는다.
- 손상된 완료 번호는 실제 fixture 회차 근거가 있을 때만 복원한다.
- 서버의 `REMOVED` 회차를 미래 경로에서 제거한다. 완료·건너뜀 번호와 변경안 번호가
  겹치면 동일 회차 대응을 확신할 수 없어 대체선을 합성하지 않는다. 현재선과 서버의
  전후 조건·비용은 유지하고 한계를 설명한다. apply를 자동 실행하지 않는다.
- 1% 미만 진행률을 공통 ProgressBar에 전달할 때 0~1 비율로 통일한다.
  확인 불가 확보액의 진행 막대는 표시하지 않는다.
- 현재·목표 라벨 간격과 SVG 글자 크기를 조정하고 목표 문구를 우측 안으로 정렬했다.
  `변화 다시 보기`는 실제 동작에 맞게 `다른 상황 비교`로 바꿨다.
  새 데모 목표 입력은 회차·Curve가 자동 생성되는 것처럼 안내하지 않는다.

## 금액 계약과 근거

읽기 전용 backend 기준: `bf424a91a02198c7890a529959eb0fdc5af734ac`.
이전 계약 조사 SHA `21f72c1fd5aa48de95eb1e1c851a93d663986a7a`와 Planner 구현 차이가 없었다.

| 호출 경로 | 확보액 의미와 처리 |
| --- | --- |
| Plan preview | Goal 초기 배정액, 완료 회차 없음. 저장 조회의 완료 합계를 무조건 차감하지 않음 |
| 새 계획 생성 | 완료 없는 생성 응답. 성공 뒤 active Plan을 재조회 |
| active·저장 상세·과거 버전 GET | `storedGoalSummary`: Goal 배정액 + 저장 회차 실행액. 현재액에 실행액 재가산 금지 |
| scenario preview | 별도 before/after와 draft ID. 현재 ViewModel을 비교 기준으로 사용 |
| 저장 draft 상세 | apply 전 완료 이력 복사 전일 수 있음. scenario before/after와 같은 객체라고 간주하지 않음 |
| apply 후 재조회 | 완료·건너뜀 이력이 복사된 새 active. 저장 조회 규칙으로 한 번만 반영 |

| 초기 배정 | 완료 입력 | 저장 조회 확보액 | 현재 표시 | 과거 누적 근거 |
| --- | --- | --- | --- | --- |
| 1,000 USD | 없음 | 1,000 | 1,000 | 초기 배정 1,000 |
| 1,000 USD | 700 | 1,700 | 1,700 | 배정 1,000 → 완료 1,700 |
| 1,000 USD | 700, 300 | 2,000 | 2,000 | 배정 1,000 → 완료 1,700 → 완료 2,000 |

초기 배정의 실제 날짜는 응답이 없으므로 별도의 과거 날짜 점을 생성하지 않는다.
`PlanController.storedGoalSummary`, `PlanResponseMapper`, `PlanScenarioService.stepChanges`,
`PlanApplyService.carryOverExecutedSteps`가 근거다. 과거 버전도 현재 Goal 엔티티를 참조하므로
불변 Goal 스냅샷으로 보장되는 것은 아니다. 서버가 각 버전의 배정 스냅샷과
before/after 회차 ID 대응을 제공하면 이 한계를 해소할 수 있다.

## 영향 / 리스크

| 사례 | 인수 코드 문제 | 후속 확인 |
| --- | --- | --- |
| 미국 1회차 기록 | 숫자는 수정됐으나 2회차 행동 불가 | 1,405 USD / 남은 1,595 / 47% / 2회차 가능 |
| 일본 1회차 기록 | 같은 차단 및 적용 경로 비교 기준 문제 | 75,000 JPY / 남은 105,000 / 42% / 2회차 가능 |
| 진행률 0.5% | 공통 막대가 50%로 해석 가능 | 비율 0.005로 전달, 원래 진행률 유지 |
| 미확인 완료 대응 | 현재와 draft 번호를 혼합해 미래선 왜곡 가능 | 변경선 생략·비교 행 유지·한계 고지 |

새로 입력한 데모 목표는 기존대로 마운트 내 입력 목록에만 남으며 자동 계획을 만들지 않는다.
확대 비교는 공통 축의 전체 경로 비교이며 변경 구간만 자동 확대하는 기능은 미구현이다.
이번에는 새 확대·재생 기능을 추가하지 않았다. AI 연결과 버전 이력은 유지했다.

## 롤백 방법

후속 수정 커밋만 `git revert <수정 커밋>`으로 되돌리고 관련 상태·세션 테스트를 실행한다.
develop 통합 merge와 기존 수정 3커밋을 무조건 되돌리지 않는다. 기존 데모 진행키 version1은
추가 시나리오 ID 필드가 선택 사항이라 구버전 데이터도 읽는다. 기존 사용자 저장소 전체를 지우지 않는다.
backend·환경변수·generated 타입·coverage 기준은 변경하지 않았다.
